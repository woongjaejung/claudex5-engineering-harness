# Claudex5 global orchestration

Apply this routing automatically when the user speaks normally; do not require them to know agent names.

1. Classify the task before delegating. Answer simple questions and make tiny, low-risk edits directly. Use the orchestration flow for multi-file, ambiguous, high-risk, or multi-stage engineering work.
2. For complex work, the main Claude session remains the coordinator. It owns requirements, architecture, task boundaries, integration, and the final report. Claude subagents cannot spawn other subagents, so do not delegate coordination to a nested agent.
3. When Superpowers `subagent-driven-development` or `executing-plans` is selected, load `claudex5-subagent-routing` before dispatching work. Superpowers owns the worktree, ledger, task loop, checkpoints, and review gates; Claudex5 owns role and model selection. Do not ask the user to choose an execution mode a second time.
4. Before implementation, Fable remains the plan owner. Run `harness_sol_plan_review` through a fresh, read-only `gpt-5.6-sol` high context when a plan crosses multiple modules or services; involves authentication, authorization, security, data migration, or destructive state; has difficult rollback, material architecture change, or high operational risk; is ambiguous or has multiple viable approaches; or contains five or more executable tasks. Use `[Codex Sol · high] Plan review` as the visible title. Skip this gate for simple plans. Require `APPROVE` or `NEEDS CHANGES`. On `NEEDS CHANGES`, Fable revises the plan and may request one fresh recheck. If that recheck still blocks, stop before implementation and ask the user; never loop or silently approve.
5. Use `harness-researcher` for read-only repository exploration when the implementation path is unclear, including independent difficult-problem analysis in a fresh context. Use `harness-implementer` for scoped implementation, including small existing-UI changes.
6. Codex is reserved for the two independent Sol reviews: `harness_sol_plan_review` and `harness_sol_adversarial_review`. Run them through `claudex5 codex-run` when available so the live graph receives lifecycle events; the wrapper selects the fixed role model and effort and never stores its prompt. Always use a read-only sandbox and prefix visible descriptions with `[Codex Sol · high]`. Manual `/codex:*` calls through the official `codex@openai-codex` plugin remain supported but are only best-effort observable. Other registered `harness_*` Codex roles are manual escape hatches: use them only when the user explicitly names one, and never use Spark for architecture, backend logic, security-sensitive behavior, data migration, broad refactors, or review.
7. After meaningful changes, run `harness-architecture-reviewer` and `harness-code-reviewer`, and add a fresh `harness_sol_adversarial_review` when risk warrants it. Reviewers do not edit.
8. Use `harness-judge` to reconcile conflicting review evidence for complex or release-sensitive work. Switch manually to `harness-judge-opus` if Fable is unavailable or the decision is high risk.
9. A language-model review never replaces deterministic verification. Run applicable build, lint, typecheck, and test commands through `claudex5 gate-run --name NAME -- COMMAND` when available and report exact results. Do not claim completion for commands that were not run.
10. Keep independent writers in non-overlapping files or isolated worktrees. Preserve user changes, inspect every delegated result, and never copy credentials into prompts, logs, commits, or artifacts.

Manual role names are escape hatches, not required syntax. If the user explicitly names a harness role or model, honor that choice unless it conflicts with safety or repository instructions.
